# Contributing to nsg

First off, thanks for taking the time to contribute!

This guide covers how to build the project, report bugs, and submit changes. Please also read:

- [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md) — how we treat each other
- [STYLE_GUIDE.md](STYLE_GUIDE.md) — code style rules (English only)
- [LICENSE](LICENSE) — AGPL-3.0

## Project structure

- `android/` — the Android app that feeds GPS data to Nikon Z-series cameras over Bluetooth smart-device mode.
- `esp32/` — the ESP32 firmware, the final product. See `esp32/README.md` for supported boards and build environments.
- `kotlin-poc/` — a Linux PoC (requires BlueZ). **Legacy**: it is no longer the development focus, but contributions are still accepted.
- `doc/` — protocol reverse-engineering notes (`doc/nikon-z-gps.md`) and the Android PoC design (`doc/android-poc.md`).

The development focus is on `android/` and `esp32/`.

## Getting started

### Android app

Requirements:

- JDK 17 or newer (a recent LTS such as 17 or 21 is recommended)
- Android SDK with platform 36 (or simply use Android Studio)
- Gradle is provided by the wrapper (`android/gradlew`)

Build:

```sh
cd android
./gradlew :app:assembleDebug
```

Run unit tests:

```sh
./gradlew :app:testDebugUnitTest
```

The debug APK is produced at `android/app/build/outputs/apk/debug/`. You can also open the `android/` folder in Android Studio and run the app on a device.

### ESP32 firmware

Requirements:

- [pioarduino](https://github.com/pioarduino/platform-espressif32)
  - Stock platformio will not work because it doesn't support latest espressif32 framework
- Board platforms and libraries are pinned in `esp32/platformio.ini`

For supported build environments, please see `esp32/README.md` for details.

Build:

```sh
cd esp32
pio run -e esp32-wroom-32e-release
```

Run unit tests (see [STYLE_GUIDE.md](STYLE_GUIDE.md) for where tests live and how they run):

```sh
pio test -e native
```

### kotlin-poc (legacy)

```sh
cd kotlin-poc
./gradlew run   # Linux with BlueZ required
```

## Reporting bugs

Before opening an issue, please search the existing issues first.

When reporting a bug, include:

- **Hardware**: phone model (Android app) or board model (ESP32), and the camera model(s) involved
- **Environment**: Android version / app version, or ESP32 environment and firmware version; camera firmware version if known
- **Steps to reproduce**, including whether the camera was previously paired with SnapBridge
- **Logs**: `adb logcat` output for Android; serial monitor output (115200 baud) for ESP32
- **Expected vs actual behavior**

Screenshots, screen recordings and photos of the ESP32 screen are welcome.

## Submitting changes (PR workflow)

> It's highly recommended to create an issue before you implement anything.

1. Fork the repository and create a dedicated branch with a descriptive name (e.g. `fix/ble-reconnect`, `feature/xxx`).
2. Keep changes focused: one logical change per PR.
3. Run the relevant tests locally (see above) and make sure they pass.
4. Update documentation if the change affects user-visible behavior or board support (`README.md`, `esp32/README.md`, `doc/`).
5. Add yourself to [CONTRIBUTORS.md](CONTRIBUTORS.md) if you haven't already.
6. Open the PR against the `master` branch.
7. If your PR uses LLM/AI in any way, you MUST declare it (see the LLM/AI policy below).
8. Commit messages must be in English (see STYLE_GUIDE.md).

Code review is done by the maintainers when they have time. **The maintainers receive no money from working on this project. Everyone is voluntary and has no obligation to answer questions or review PRs.** We will do our best, but we don't owe you anything.

## Language policy

- English is the primary language of this project: code, comments, commit messages and documentation are all in English and should be considered as the single truth when multi-lang translation exists.
- For issues and PRs, English is encouraged, but Chinese is also fine. If you post in Chinese, an English translation is welcome (but not required). Translators and LLMs make this easy.
- Code and code comments MUST be in English, unless the code is part of a localization mechanism (e.g. UI strings).

## LLM/AI policy

This project allows the use of LLMs and AI assistants to help with coding and project work, **but it must be used responsibly**:

- **No vibe coding.** You MUST NOT generate code with an LLM/AI and submit it without understanding what it does. Only submit work you can explain; if you don't understand it, don't submit it.
- **Nobody is obligated to read LLM output.** If an issue or PR was entirely generated by an LLM, maintainers and other contributors are free to ignore it entirely.
- **LLM usage in PRs must be declared.** If you used an LLM/AI for a PR, explicitly state it in the PR description:
  - which model or tool you used,
  - how you used it (e.g. generating code, writing the description, reviewing your own changes, translating).
  - This is for transparency and should not affect the PR review. If it's a good PR generated by LLM, we will happily accept it.
- **LLM/AI reviews are informational only.** Maintainers may use LLMs to help review PRs, but that output is for their own reference only. It should never be a requirement for you to fix anything, unless human reviewer reference them in their own review.
- **Final decisions are made by humans.** Approvals and change requests (APPROVAL / REQUEST_CHANGES) must be written by a human. An automated or AI-generated review will never be treated as a formal decision.
